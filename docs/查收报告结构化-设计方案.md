# 查收报告结构化：问题有编码、一次查全、多轮可比（设计方案）

> 状态：草案，2026-10-11。目标版本 v3.0。借鉴：pandera（一次收集全部错误，再统一报告）、Frictionless（错误有固定编码）、
> Great Expectations（同一份结果既给机器读，也渲染给人看）。
> 和《填报规则-设计方案》的关系：规则表要新增 6 个错误编码。建议**先做本方案的骨架**，再在上面加规则表，
> 免得新的错误类型先按现在的字符串写法写一遍、再返工一遍。

## 1. 现状和问题

`analyze` 已经是「一次查全」：逐人把所有问题都列出来，不会在第一个错处停下。问题出在**结果的形状**：

| 字段 | 现在的样子 | 问题 |
|---|---|---|
| `p["blanks"]` | `[{col, count, rows, no_col}]` | 已经是结构化的，好 |
| `p["changes"]` | `["少了 1 行", "第 7 行和下发时不一样（改了「客户名称」）"]` | 是**拼好的句子**，程序没法再判断是哪类改动 |
| `p["notes"]` | `["「x.xlsx」打不开：…", "「a」和「b」内容完全一样…"]` | 自由文字；`_judge` 和 `notice_text` 里有 `"打不开" in n` 这种**靠搜字判断**的写法 |
| 技能输出 | 只有 `counts` 和整段通报文字 | 用户接着问「东城还差什么」「只给有漏填的人发催办」，AI 只能回去读通报文字 |
| 回收记录.json | 每轮只记谁交了、谁合格 | 只能说出「比上次新交了谁」，说不出「东城漏填从 5 行降到 1 行」 |

最后一行是用户看得见的损失：第二轮、第三轮查收时，最想知道的是**谁改好了、谁还没改**。

## 2. 做法

### 2.1 每个人一张问题清单 `p["issues"]`

```python
{"code": "blank", "sheet": "走访", "col": "走访日期", "count": 5, "rows": [3, 7, 9, 12, 15]}
{"code": "rows_lost", "sheet": "走访", "count": 1}
{"code": "unreadable", "file": "东城.et", "why": "et"}
{"code": "same_as", "file": "东城.xlsx", "other": "西城.xlsx"}
```

**只有名字、列名、文件名、行号、个数和编码，不含任何单元格的值**，和下发记录的隐私口径一致。

### 2.2 编码表（定下来以后只加不改）

| 编码 | 归到哪个状态 | 要不要催 | 现在对应的文字 |
|---|---|---|---|
| `missing` | 未交 | 催 | 还没收到你的表 |
| `empty` | 空表 | 催 | 只有表头，没填数据 |
| `blank` | 有漏填 | 催 | 走访日期 漏 5 行（第 3、7…行） |
| `no_col` | 有漏填 | 催 | 没有「走访日期」这一列 |
| `not_in_options` `not_date` `not_number` `not_whole` `not_mobile` `not_phone` | 填写有误 | 催 | 规则表方案新增 |
| `col_deleted` | 有改动 | 催 | 删了「客户名称」列 |
| `rows_lost` / `rows_added` | 有改动 | 催 | 少了 / 多了 N 行 |
| `rows_changed` | 有改动 | 催 | 第 7 行和下发时不一样（改了「客户名称」） |
| `header_mismatch` | 表头对不上 | 催 | 「走访」表头和别人的对不上，没法查 |
| `unreadable` | 表头对不上（没法查） | 催 | 打不开：是 WPS 表格自己的格式… |
| `no_header` | 表头对不上（没法查） | 催 | 认不出表头 |
| `old_version` | 不影响状态 | 只注明 | 是同一份表的旧版本，按最新的查 |
| `same_as` | 不影响状态 | 只注明 | 和「西城.xlsx」内容完全一样，请核对是否交错了表 |
| `not_in_total` | 未交 | 催 | 表里没有这个名字的行（总表模式） |

三张小表放在 `collect.py` 里，替代现在散落各处的判断：

```python
ISSUE_STATUS = {"blank": ST_PARTIAL, "no_col": ST_PARTIAL, "rows_lost": ST_CHANGED, ...}
ISSUE_TEXT   = {"blank": lambda i: f"{i['col']} 漏 {i['count']} 行（{_rows_text(i['rows'], i['count'])}）", ...}
ISSUE_NAG    = {...}   # 催 / 只注明
```

`_judge` 只负责产出 issues；状态由 `ISSUE_STATUS` 推出来，规则和现在一样：`flags` 是所有 issue 对应状态的集合，按 `_RANK` 取最重的那个当 `status`。`"打不开" in n` 这类搜字判断一律改成看编码。

### 2.3 兼容：旧字段由 issues 推出来，一个都不删

`p["blanks"]`、`p["changes"]`、`p["notes"]` 照样存在，改成在 `_judge` 末尾**从 issues 生成**。这样 `notice_text`、`write_progress`、`run_collect`、内部技能都不用同步改，之后再逐个换成直接读 issues。

### 2.4 新产出：回收结果.json

每次查收在输出目录多写一个文件：

```json
{"version": 1, "title": "九月走访", "time": "2026-10-11T15:20:00", "due": "10月15日 18:00",
 "counts": {"expected": 12, "submitted": 9, "ok": 5, "missing": 3, "partial": 2, "invalid": 1, "changed": 1},
 "people": [{"name": "东城", "status": "有漏填", "flags": ["有漏填"], "files": ["东城.xlsx"], "rows": 40,
             "issues": [{"code": "blank", "col": "走访日期", "count": 5, "rows": [3, 7, 9, 12, 15]}]}],
 "extra": ["别的科室.xlsx"]}
```

- 给技能和内部版用：`er_check` 的输出加一个 `people` 字段（就是这个结构）。AI 被追问「东城还差什么」「把有漏填的人的催办话术单独列出来」时，直接查这份数据，不用回去解析通报文字。
- `[SUMMARY]` 加一个 `result` 键，指向这个文件。GUI 暂时不用读它。

### 2.5 多轮对比：说出「谁改好了、谁还差」

`回收记录.json` 每轮多记一项，按人记**问题的编码和个数**（不记行号，文件小）：

```json
{"time": "...", "submitted": [...], "ok": [...],
 "issues": {"东城": {"blank": 5}, "西城": {"not_date": 1, "rows_lost": 1}}}
```

第二轮起，通报的「比上次」一节从一行扩成三行：

```
比上次：
  新交：南城、北城
  改好了：西城
  还差：东城 漏填 5 行 → 1 行
```

没有上一轮的问题记录时（旧版写的回收记录），只显示「新交」，和现在一样。

## 4. 实施顺序和测试

1. **先锁住现在的行为**：在改代码之前，给 `tests/test_collect.py` 现有的几个场景（未交、空表、漏填、改动、对不上、读不了、重复交）补一组**通报全文快照**，把现在的输出存成期望值；
2. 加编码表，`_judge` / `_diff` 改成产出 issues，旧字段由 issues 推出来。**快照必须一字不差地通过**，这一步是纯重构；
3. 写回收结果.json，加 `er_check` 的 `people`；
4. 回收记录.json 每轮记问题，通报加「改好了 / 还差」；
5. 再接《填报规则》的新编码（6 个「填写有误」类编码直接写进编码表）。

新增测试：

- 每个编码至少一个场景，检查 code、count、rows；
- json 里不出现任何单元格的值（构造一个带特殊内容的格子，断言整份 json 里搜不到它）；
- 两轮对比：第一轮漏 5 行，第二轮漏 1 行，另一个人改好了，通报出现「改好了」「5 行 → 1 行」；
- 旧版回收记录（没有 `issues` 键）照样能比，只出「新交」。

工作量：第 1～2 步最大（`_judge`、`_diff`、`analyze` 三个函数），但有快照守着，风险可控；第 3～4 步各是几十行。
